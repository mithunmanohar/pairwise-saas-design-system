# Pairwise: a production-grade design system for ML platforms, AI applications and SaaS

**One set of design tokens and 42 accessible React components. Every app built on it looks and behaves the same, whether a person or an AI agent wrote the screen.**

## Why Pairwise

ML and AI systems rarely ship as a model alone. An end-to-end solution needs a full-stack application around it: dashboards for model and pipeline health, consoles for training, evaluation and agent workflows, and multi-tenant admin apps for the people who rely on the system. More and more of that application code is written by AI coding agents.

Without a shared foundation, every agent session starts from a blank page: a new button, a new shade of grey, a new table, a new way to show "failed". Each screen looks fine on its own. Across projects nothing matches, accessibility is left to chance, and the same bug gets fixed in five places.

Pairwise solves this at the platform level. Decisions are made once, encoded in tokens and components, and enforced by tooling. It targets **ML platform and infrastructure consoles, LLM and agentic AI tooling, AIOps and observability dashboards, and multi-tenant SaaS admin apps**, and it is built to be used by AI coding agents as well as by people.

The result: asked for "a page showing why this CI run failed", an agent builds it from `PageHeader`, `StatusGrid`, `CodeBlock` and `Timeline` instead of inventing them. Every app gets the same status language, the same keyboard behaviour and the same dark mode.

## Design principles, and how they're enforced

A principle that isn't enforced is a suggestion. Each one below is backed by code, a test or a lint rule.

| Principle | What it means | How it's enforced |
|---|---|---|
| **Signal, not decoration** | Neutral chrome, no brand accent. `status-critical` is the only colour that asks a person to act, so on a busy screen the one red thing is the thing to look at. | Tokens-only CSS lint rejects raw colours in component styles. |
| **Status grammar** | Status is always icon + label + colour, never colour alone (WCAG 1.4.1). Healthy is quiet: an icon and text, no tint. | One `StatusBadge` component; the icon shapes differ, so states read without colour. |
| **One source of truth** | Every colour, space, radius and type style lives in [`tokens.json`](design-system/tokens.json): 31 colour tokens × 2 themes, 8 spacing steps, 8 type styles. | A small generator emits CSS variables and typed TypeScript names (`ColorToken`), so a typo in a colour name is a compile error. |
| **Contrast with margin** | Text ≥ 4.8:1 and UI ≥ 3:1 on every surface, both themes. That's above the AA minimum, so rendering differences can't fail it. | Unit tests compute WCAG contrast for every token pair on every run. |
| **Colour-blind-safe charts** | Five categorical colours whose worst adjacent pair stays ≥ 11 ΔE2000 under normal, protan, deutan and tritan vision (worst case: 14.9 light, 16.2 dark). | Unit tests simulate colour-vision deficiency and fail the build below 11. |
| **Behaviour from proven primitives** | Focus traps, Escape, arrow keys and screen-reader roles come from Radix (dialog, select, menu, checkbox, switch), styled with our own classes. | Checked in a real browser during development: focus wraps, Esc closes, focus returns. Keyboard tests in CI are on the roadmap. |
| **Theme and density parity** | Light and dark are equals. Compact (32 px rows) for working views, comfortable (40 px) for overviews, from the same components. | One `data-theme` and one `data-density` attribute on `<html>`; nothing else changes. |
| **Writing is design** | Sentence case, verb + object buttons ("Roll back to v2.14.0", never "OK"), errors that say how to fix it, no emoji. | [Guidelines](design-system/GUIDELINES.md) plus every component's README. AI agents read them via `COMPONENTS.md`. |

## Why it's production grade

- **Typed end to end.** Strict TypeScript (`noUncheckedIndexedAccess`) with **zero `any`**. `DataTable<Row>` infers your row type, so `render` and `onRowClick` are typed. Type-level tests compile against the *built* package to prove the published types work.
- **One package, versioned.** `@pairwise/ui` ships ESM, generated `.d.ts`, `tokens.css`, `styles.css` and self-hosted fonts. Releases follow semver with a [CHANGELOG](packages/ui/CHANGELOG.md).
- **Quality gates on every PR** ([`ci.yml`](.github/workflows/ci.yml)): build, typecheck (package + examples + type tests), the tokens-only lint, and unit tests (contrast, colour-vision separation, generators). It also fails if generated files weren't committed.
- **Refactors proven pixel-identical.** A capture harness ([`scripts/capture-previews.mjs`](scripts/capture-previews.mjs)) screenshots every component in both themes and both densities and diffs them pixel by pixel. Rebuilding the preview kit from the package changed **0 of 180** captures (fonts aside). Moving Modal and Drawer onto Radix (with five new form controls) changed **0 of 132**, and the next five components changed **0 of 152** existing ones.
- **Live site on every merge** ([`pages.yml`](.github/workflows/pages.yml)): CI runs, then the demo, catalogue and landing page deploy to GitHub Pages.
- **Release pipeline** ([`release.yml`](.github/workflows/release.yml)): push `v1.2.0` and CI builds and verifies the package, then publishes it to a `ui-v1.2.0` git tag. Projects install with one command: no registry, no tokens.
- **Docs that can't drift.** The catalogue and `COMPONENTS.md` are generated from the same cards and READMEs the components are tested with.
- **Permissive licences only:** MIT, Apache-2.0 and OFL.

## Building with AI agents

This repository was itself built with AI coding agents (Claude Code), under the same discipline it asks of apps:

1. **Rules written down first.** [`CLAUDE.md`](CLAUDE.md) holds the visual rules, the non-negotiables (tokens only, accessibility floors, what needs approval) and the repo map. [`DECISIONS.md`](design-system/DECISIONS.md) records the why.
2. **Small, reviewable steps.** Each step ends with a written summary: what changed, how it was verified, and the decisions it needs from a human.
3. **Automated gates, not trust.** Contrast tests, type tests, lint, pixel diffs and in-browser behaviour checks, before anything merges.
4. **Agents consume the system.** Every project gets this in its `CLAUDE.md`, so its agents read the docs instead of inventing UI:

```md
## UI: Pairwise design system
- All UI uses `@pairwise/ui`. Before building any UI, read `node_modules/@pairwise/ui/dist/COMPONENTS.md`.
- Don't create your own buttons, inputs, tables, menus, modals, toasts or badges, and don't add another UI library.
- Your own CSS uses Pairwise variables only (`var(--space-4)`, `var(--surface-raised)`); never hard-code colours.
- Status is always `StatusBadge`. Sentence case, no emoji.
- Missing a component? Use the closest one and leave a `TODO(pairwise):` instead of building a new one.
```

The point isn't that AI wrote the code. It's that the output is **consistent, accessible and verifiable** because the system around the AI is.

## Use it

```bash
pnpm add github:mithunmanohar/pairwise-saas-design-system#ui-v1.0.0
```

```tsx
import "@pairwise/ui/fonts.css";
import "@pairwise/ui/tokens.css";
import "@pairwise/ui/styles.css";
import { PairwiseProvider, Toaster, toast, Button, TextInput } from "@pairwise/ui";

export function App() {
  return (
    <PairwiseProvider>
      <TextInput label="Branch name" placeholder="feature/add-retry" />
      <Button variant="primary" onClick={() => toast("Branch created")}>Create branch</Button>
      <Toaster />
    </PairwiseProvider>
  );
}
```

Set `data-theme="dark"` and `data-density="comfortable"` on `<html>` to switch. Full guide: [`packages/ui/README.md`](packages/ui/README.md).

## Repository map

| Path | What's in it |
|---|---|
| [`design-system/`](design-system) | Tokens (`tokens.json`), rules ([README](design-system/README.md), [GUIDELINES](design-system/GUIDELINES.md), [DECISIONS](design-system/DECISIONS.md)), one card + README per component, the generated catalogue |
| [`packages/ui/`](packages/ui) | `@pairwise/ui`: components, styles, generators, tests |

| [`.github/workflows/`](.github/workflows) | CI on every PR; the Pages site on every merge; a release on every version tag |

**Change it:** open a PR (CI runs every gate), add a CHANGELOG line, and bump the version (fix → patch, new component → minor, breaking → major). After merging, `git tag vX.Y.Z && git push origin vX.Y.Z` releases it. Regenerate the images with `pnpm -C examples screenshots`.
