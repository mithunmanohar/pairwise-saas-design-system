# Pairwise: a production-grade design system for AI applications and multi-tenant SaaS

[![CI](https://github.com/mithunmanohar/pairwise-saas-design-system/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/mithunmanohar/pairwise-saas-design-system/actions/workflows/ci.yml?query=branch%3Amain)

**One set of design tokens and 59 accessible React components. Every app built on it looks and behaves the same, whether a person or an AI agent wrote the screen.**

## Why Pairwise

ML and AI systems rarely ship as a model alone. An end-to-end solution needs a full-stack application around it: dashboards for model and pipeline health, consoles for training, evaluation and agent workflows, and multi-tenant admin apps for the people who rely on the system. More and more of that application code is written by AI coding agents.

Without a shared foundation, every agent session starts from a blank page: a new button, a new shade of grey, a new table, a new way to show "failed". Each screen looks fine on its own. Across projects nothing matches, accessibility is left to chance, and the same bug gets fixed in five places.

Pairwise solves this at the platform level. Decisions are made once, encoded in tokens and components, and enforced by tooling. It targets **ML platform and infrastructure consoles, LLM and agentic AI tooling, AIOps and observability dashboards, and multi-tenant SaaS admin apps**, and it is built to be used by AI coding agents as well as by people.

The result: asked for "a page showing why this CI run failed", an agent builds it from `PageHeader`, `StatusGrid`, `CodeBlock` and `Timeline` instead of inventing them. Every app gets the same status language, the same keyboard behaviour and the same dark mode.

## What you can build with it

A complete ops and developer-platform app, built **only** from the package (source in [`examples/src/screens`](examples/src/screens)). Every item in the side navigation is a working page, and list rows open detail pages. CI type-checks all of it, so it can only use the public API. **[Try it live](https://mithunmanohar.github.io/pairwise-saas-design-system/demo/)**: the nav, search, tabs, filters, menus, dialogs, drawers and toasts all work, dashboards update every few seconds, and a switch flips theme and density. Dark is the default; every screen works in light too.

### Ownership: one hierarchy, one scope
Everything is owned somewhere in a hierarchy: company, business function, squad, initiative, project, and the
repositories, services and cost workspaces under them. The **Resource explorer** is the only page that shows the whole
tree. The tree shows each node's worst status with a count (healthy stays quiet), a no-access function stays greyed
for context, and resources load in groups by type. The workspace has the same tabs for every node (overview,
resources, delivery, observability, infrastructure, financials), and every count says what it includes ("0 direct · 7
with everything below").

![Resource explorer with the AI transformation initiative selected, dark theme](docs/images/screens/explorer-dark.png)

The chosen node becomes the **ownership scope** in the top bar. It sits beside the runtime scope (environment / region
/ cluster), not inside it, and is kept in the URL (`#/runs?scope=fn-commerce`). Every list page then filters by it,
says what it covers in one line, and shows each row's path *below* the scope, never the levels above it. A switch
turns any of these tables into a **Tree** grouped by owner, with rollups on collapsed rows: worst status with a count,
sums, the latest time.

### Personalisation: fonts, theme and density
An app picks its default font with one attribute (`data-font` on `<html>`), and each person can choose their own in "Your preferences", next to theme and density; the choice is saved in their browser. The account menu (the avatar) shows who is signed in and their role, switches organization, and opens those preferences. Four presets ship, all open-licence and self-hosted, and only the one in use downloads: **Atkinson Hyperlegible** (the default, drawn so I/l/1 and O/0 can't be confused), **Inter** with IBM Plex Mono, **IBM Plex** Sans and Mono, and the device's **system font**. A preset changes only the typeface, so every layout holds: each demo page was checked in every preset from 1440 down to 360 px.

## Design principles, and how they're enforced

A principle that isn't enforced is a suggestion. Each one below is backed by code, a test or a lint rule.

| Principle | What it means | How it's enforced |
|---|---|---|
| **Signal, not decoration** | Neutral chrome, no brand accent. `status-critical` is the only colour that asks a person to act, so on a busy screen the one red thing is the thing to look at. | Tokens-only CSS lint rejects raw colours in component styles. |
| **Status grammar** | Status is always icon + label + colour, never colour alone (WCAG 1.4.1). Healthy is quiet: an icon and text, no tint. | One `StatusBadge` component; the icon shapes differ, so states read without colour. |
| **One source of truth** | Every colour, space, radius and type style lives in [`tokens.json`](design-system/tokens.json): 31 colour tokens × 2 themes, 8 spacing steps, 8 type styles. | A small generator emits CSS variables and typed TypeScript names (`ColorToken`), so a typo in a colour name is a compile error. |
| **Contrast with margin** | Text ≥ 4.8:1 and UI ≥ 3:1 on every surface, both themes. That's above the AA minimum, so rendering differences can't fail it. | Unit tests compute WCAG contrast for every token pair on every run. |
| **Colour-blind-safe charts** | Five categorical colours whose worst adjacent pair stays ≥ 11 ΔE2000 under normal, protan, deutan and tritan vision (worst case: 14.9 light, 16.2 dark). | Unit tests simulate colour-vision deficiency and fail the build below 11. |
| **Behaviour from proven primitives** | Focus traps, Escape, arrow keys, typeahead and screen-reader roles come from Radix (dialog, popover, menu, select, tabs, tooltip, toast, radio, checkbox, switch), cmdk (search, commands and combobox), react-day-picker (calendars) and React Aria (trees), styled with our own classes. | 84 Playwright tests in Chromium on every PR: keyboard paths, focus return, Escape order in nested overlays, live regions, the ownership scope across pages. axe-core finds no WCAG 2.2 A/AA violations on any of the 59 cards or 14 demo routes, in either theme. |
| **Theme and density parity** | Light and dark are equals. Compact (32 px rows) for working views, comfortable (40 px) for overviews, from the same components. | One `data-theme` and one `data-density` attribute on `<html>`; nothing else changes. Every card is captured and axe-checked in both themes. |
| **Calm, optional motion** | Menus and popovers fade 4 px from their trigger; dialogs fade in, drawers slide in. Nothing decorative. | Durations and layers are tokens; the lint rejects raw durations and z-index values. `prefers-reduced-motion` sets every duration to 0 ms, which a test checks. |
| **Writing is design** | Sentence case, verb + object buttons ("Roll back to v2.14.0", never "OK"), errors that say how to fix it, no emoji. | [Guidelines](design-system/GUIDELINES.md) plus every component's README. AI agents read them via `COMPONENTS.md`. |

## Why it's production grade

- **Typed end to end.** Strict TypeScript (`noUncheckedIndexedAccess`) with **zero `any`**. `DataTable<Row>` infers your row type, so `render` and `onRowClick` are typed. Type-level tests compile against the *built* package to prove the published types work.
- **One package, versioned.** `@pairwise/ui` ships ESM, generated `.d.ts`, `tokens.css`, `styles.css` and self-hosted fonts. Releases follow semver with a [CHANGELOG](packages/ui/CHANGELOG.md).
- **Quality gates on every PR** ([`ci.yml`](.github/workflows/ci.yml)): build, typecheck (package + examples + type tests), the tokens-only lint (colours, layers, durations), unit tests (contrast, colour-vision separation, generators), and Playwright behaviour + axe accessibility tests in Chromium. It also fails if generated files weren't committed.
- **Refactors proven pixel-identical.** A capture harness ([`scripts/capture-previews.mjs`](scripts/capture-previews.mjs)) screenshots every component in both themes and both densities and diffs them pixel by pixel. Rebuilding the preview kit from the package changed **0 of 180** captures (fonts aside). Moving Modal and Drawer onto Radix (with five new form controls) changed **0 of 132**, and the next five components changed **0 of 152** existing ones. For 2.0, every visible change to an existing card was reviewed in a before/after diff across 2 themes × 2 densities.
- **Live site on every merge** ([`pages.yml`](.github/workflows/pages.yml)): CI runs, then the demo, catalogue and landing page are published to the `gh-pages` branch, which GitHub Pages serves.
- **A preview for every pull request** ([`pr-preview.yml`](.github/workflows/pr-preview.yml)): the demo and catalogue built from the PR's branch, at `/pr-preview/pr-<number>/` beside the live site, linked from a comment on the PR and removed when it closes. The live site doesn't change until the merge.
- **Release pipeline** ([`release.yml`](.github/workflows/release.yml)): push `v1.2.0` and CI builds and verifies the package, then publishes it to a `ui-v1.2.0` git tag. Projects install with one command: no registry, no tokens.
- **Docs that can't drift.** The catalogue and `COMPONENTS.md` are generated from the same cards and READMEs the components are tested with.
- **Permissive licences only:** MIT, Apache-2.0 and OFL.

## Building with AI agents

This repository was itself built with AI coding agents (Claude Code), under the same discipline it asks of apps:

1. **Rules written down first.** [`CLAUDE.md`](CLAUDE.md) holds the visual rules, the non-negotiables (tokens only, accessibility floors, what needs approval) and the repo map. [`DECISIONS.md`](design-system/DECISIONS.md) records the why.
2. **Small, reviewable steps.** Each step ends with a written summary: what changed, how it was verified, and the decisions it needs from a human.
3. **Automated gates, not trust.** Contrast tests, type tests, lint, pixel diffs and in-browser behaviour checks, before anything merges.
4. **Agents consume the system.** Every project gets this in its `CLAUDE.md`, so its agents read the docs instead of inventing UI:

```md
## UI: Pairwise design system
- All UI uses `@pairwise/ui`. Before building any UI, read `node_modules/@pairwise/ui/dist/COMPONENTS.md`.
- Don't create your own buttons, inputs, tables, menus, modals, toasts or badges, and don't add another UI library.
- Your own CSS uses Pairwise variables only (`var(--space-4)`, `var(--surface-raised)`); never hard-code colours.
- Status is always `StatusBadge`. Sentence case, no emoji.
- Missing a component? Use the closest one and leave a `TODO(pairwise):` instead of building a new one.
```

The point isn't that AI wrote the code. It's that the output is **consistent, accessible and verifiable** because the system around the AI is.

## Use it

```bash
pnpm add github:mithunmanohar/pairwise-saas-design-system#ui-v1.0.0
```

```tsx
import "@pairwise/ui/fonts.css";
import "@pairwise/ui/tokens.css";
import "@pairwise/ui/styles.css";
import { PairwiseProvider, Toaster, toast, Button, TextInput } from "@pairwise/ui";

export function App() {
  return (
    <PairwiseProvider>
      <TextInput label="Branch name" placeholder="feature/add-retry" />
      <Button variant="primary" onClick={() => toast("Branch created")}>Create branch</Button>
      <Toaster />
    </PairwiseProvider>
  );
}
```

Set `data-theme="dark"`, `data-density="comfortable"` and `data-font="inter"` (or `plex`, `system`) on `<html>` to switch. Full guide: [`packages/ui/README.md`](packages/ui/README.md).

| Path | What's in it |
|---|---|
| [`design-system/`](design-system) | Tokens (`tokens.json`), rules ([README](design-system/README.md), [GUIDELINES](design-system/GUIDELINES.md), [DECISIONS](design-system/DECISIONS.md)), one card + README per component, the generated catalogue |
